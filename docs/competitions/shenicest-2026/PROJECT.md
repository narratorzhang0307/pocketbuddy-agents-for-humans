### 作品描述

Pocket Buddy 希望让人们从“知道应该照顾自己”，走到“愿意迈出今天的一小步”。用户可以带着 3D 伙伴走进城市，在地图上探索、收集种子、种下虚拟植物，留下与地点有关的小记忆；也可以和 Frost 对话，根据自己的目标、餐食和运动记录，找到下一件适合自己的事。

作品以 Photos、Earth、Agents 三个入口组织体验：Photos 记录饮食，Earth 承载城市探索和伙伴养成，Agents 提供 Frost 与专业 Skill。可选的电子徽章把按键说话、角色状态和语音回应带到手机之外，让陪伴不只停留在聊天窗口里。

这里的“游戏”不是脱离生活的独立关卡，而是对散步、观察和自我照顾的轻量游戏化。项目不把虚拟种树等同于现实植树，也不把模型建议等同于医疗结论。

## 2. 项目背景

日常生活中，运动、饮食记录、路线规划和兴趣探索往往分散在不同应用里。用户需要反复解释自己的目标，也需要靠意志力不断回到枯燥的记录页面。另一类 AI 应用能给出很多建议，却不一定能把建议接到一个具体、可执行的动作上。

Pocket Buddy 从两个问题出发：

1. 能否用一个持续陪伴的角色，把“记录—理解—行动—反馈”连接起来？
2. 能否让一段普通的散步，变成和伙伴一起探索、收集与留下记忆的过程？

我们的设计选择是：由 Frost 承接交流和上下文，由地图与专业 Skill 承接行动，由明确的事件与用户确认记录结果。可爱的角色负责降低开始行动的门槛，真实的数据边界负责避免过度承诺。

## 3. 目标用户与使用场景

以下是产品定位与待验证的用户假设，不代表已经完成大规模用户调研。

| 目标用户 | 典型需求 | Pocket Buddy 的对应体验 |
| --- | --- | --- |
| 久坐、想增加日常活动的城市用户 | 很难开始复杂训练，希望先动起来 | 带伙伴散步、地图探索、虚拟种植和轻量反馈 |
| 独自运动、需要鼓励与记录的人 | 希望有人理解目标，并把建议变成行动 | Frost 对话、健康记忆、训练与路线 Skill |
| 喜欢宠物、自然和轻量养成的用户 | 希望日常路线有更多发现与情感联系 | 3D 同行伙伴、种子与植物收藏、自然观察入口 |
| 想减少运动中操作手机的人 | 希望通过简单语音获得回应 | 可选的电子徽章按键输入和状态反馈 |

典型场景是下班后的一次短途散步：用户打开 Earth，选择同行角色，开始地图探索，在喜欢的位置种下一株虚拟植物；结束后再与 Frost 交流今天的运动或饮食。具备相应权限、设备与服务时，也可以从对话进入训练页面，或通过徽章发起语音交互。

## 4. 当前作品的主要功能

### 4.1 Earth：和伙伴一起走进城市

中间的 Earth 页面复用真实地图组件，叠加可行走的 3D 角色、伙伴、种子背包、虚拟植物和自然观察入口。角色模型由 Three.js 加载，包含已制作好的 GLB 与动画资源。

地图既有便于演示的漫游交互，也有需要定位授权的真实 GPS 模式。二者不能混为一谈：演示角色移动和游戏进度不是手机计步器的健康记录；真实 GPS 语音种树还需要有效的定位状态与新鲜定位数据。

源码入口：[EarthActionMapTab](../../../src/app/components/EarthActionMapTab.tsx)、[StreetGardenLab](../../../vendor/legacy-city/src/app/components/StreetGardenLab.tsx)、[3D 角色配置](../../../vendor/legacy-city/src/app/lib/agent3d/profiles.ts)。

### 4.2 Frost：连续的伙伴对话与任务入口

Frost 负责理解用户的表达、读取被允许使用的上下文，并将明确的请求交给已注册的 Skill。手机文字输入和徽章语音转写共用同一套会话运行逻辑，外设不是另一个拥有独立记忆的“聊天机器人”。

运行时具备步骤数、工具调用数、超时、取消和审批边界。等待用户或外部事件时保持等待，不用一段模型回复冒充真实完成。模型不可自由调用任意设备操作，也不可直接把未经确认的候选信息写成健康事实。

源码入口：[Frost 对话运行时](../../../src/app/lib/frostAgentRuntime.ts)、[Frost Agent 架构](../../../frost-agent/README.md)。

### 4.3 Photos：从一张餐食照片到可确认的记录

当前 Photos 首页是餐食记录入口。用户选择图片后，还需要明确发起识别；前端会压缩并重新编码图片，再调用服务端图像识别与分割链路。结果以候选菜品、份量和热量估计呈现，用户可以修改或手动录入，确认之后才形成餐食记录。

拍照不等于精确称重，模型识别也不是营养诊断。示例餐食与真实记录分开，原始照片不作为健康记忆里的必要字段。

源码入口：[FoodPhotosTab](../../../src/app/components/FoodPhotosTab.tsx)、[图像处理服务](../../../server/photo-harness.mjs)。

### 4.4 运动与健康 Skill

项目整合了“练了吗”和 Her Motion 两个子应用，并通过统一的任务交接与结果消息连接到主应用。它们不是简单的外链截图：源码中包含子应用构建、内嵌页面、会话消息和停止处理。

不同能力的运行条件不同。Her Motion 使用本地 MediaPipe 资源；练了吗的完整动作分析还依赖独立部署的模型服务及权重。摄像头是否获准、模型是否就绪、动作是否完成，需要分别判断；页面打开不能作为训练完成的证据。

健康记忆保留记录的来源、时间和修订关系。用户对云端分析和徽章播报分别授权，避免把所有健康信息默认交给所有入口。

源码入口：[练了吗](../../../lianlema-portable/app_project/README.md)、[Her Motion](../../../vendor/her-motion/README.md)、[整体架构](../../../ARCHITECTURE.md)。

### 4.5 可选硬件：把 Frost 带到口袋之外

本次源码中可直接核对的是 OJBadge / ESP32-S3 徽章固件及 iOS 原生桥接，包括圆屏角色状态、实体键语音输入、蓝牙数据传输和音频反馈。它是手机应用的交互外设，而不是独立运行大模型的设备。

典型链路为：实体按键采音 → 蓝牙传至 iPhone → 手机端语音识别 → Frost 会话 / Skill → 屏幕或经授权的语音回应。手机权限、连接状态、服务配置和实际扬声器播放是各自独立的条件。

本次上传只交付源码，不执行刷机、安装或真机验收。历史设备记录不等于本次新提交已经在同一设备重新验证。当前 BLE 链路还需要进一步完善设备归属、配对和访问控制，不适合作为无保护的公共设备开放。

源码入口：[iOS 徽章桥接](../../../native/frost-badge/ios/README.md)、[徽章固件](../../../hardware/ojbadge-agent-link/README-OJBADGE.md)。

## 5. 游戏玩法说明

### 5.1 核心循环

**选择同行伙伴 → 探索城市 → 收集与使用种子 → 种下虚拟植物 → 留下地点记忆 → 回访与继续探索。**

这是一个以探索、收集和陪伴为主要动机的轻量养成原型，没有必须击败的敌人或统一通关结局。

### 5.2 一次体验如何进行

1. **进入 Earth。** 选择角色与同行伙伴，查看地图和当前可用的植物资源。
2. **准备种子。** 从已解锁的种子中选择随身携带的种类；当前种子袋上限为 6 种。
3. **开始探索。** 演示漫游用于体验角色和地图交互；真实散步模式需要用户允许定位。
4. **种下植物。** 普通种植使用对应种子库存，把虚拟植物放到地图落点，可附上地点或一句话等信息。
5. **观察成长。** 当前植物采用约 12 秒的快速成长动画，用于即时反馈，并非现实植物生长模拟。
6. **回到旧地点。** 植物记录保存在本机，支持附近回访记录；同一植物的回访计数有 6 小时间隔，避免原地反复刷计数。
7. **继续行动。** 游戏进度中有累计步数里程碑与种子解锁逻辑，也可以转到 Frost 或运动 Skill 继续今天的活动。

### 5.3 语音种树是一条独立的轻交互

当前实现支持明确的“进入地图模式”“种一棵树”等整句命令。语音种树要求地图处于前台、已进入真实 GPS 散步，并取得足够新鲜且精度合格的定位；失败时返回未种植，不把命令排队到未来自动执行。

这条入口生成的是本机地图上的散步纪念树，**不消耗种子袋库存，也不代表获得运动奖励**。每次输入有独立标识，以避免重复处理同一句输入造成重复种植。

### 5.4 演示与实际数据的边界

- 游戏进度模块目前含有每日 **3,000 步的演示保底值**，部分步数由距离估算；因此不能把游戏面板的全部数值当作 HealthKit 实测数据或防作弊凭据。
- 地图植物为 `device-local` 存储。代码中的 `public` 显示属性不等于已同步给其他用户，目前不宣称完整的多人共享世界。
- 虚拟植物和角色成长是数字反馈，不代表现实植树、碳减排或健康疗效。
- 此次文档不宣称用户可以实时调用 Tripo API 生成任意 3D 角色；当前可核对的是预生成模型、动画配置及运行时加载。

玩法源码：[进度与种子](../../../vendor/legacy-city/src/app/lib/pocket-plants/progression.ts)、[种植与回访](../../../vendor/legacy-city/src/app/lib/pocket-plants/planting.ts)、[真实 GPS 语音种树](../../../vendor/legacy-city/src/app/lib/pocket-plants/voicePlanting.ts)。

| 层次 | 主要技术 | 在作品中的职责 |

| 独立分析服务 | Python / FastAPI、姿态与动作分析模型、SAM 相关服务 | 为配置完备的图像和运动链路提供实际推理 |

系统的核心关系是：**用户提出请求 → Frost 读取被授权的上下文 → 运行时选择已注册能力 → 页面、服务或设备产生结果 → 结果经过校验或用户确认 → 更新记忆与界面。**

Skill Canvas 已有画布编辑、校验、编译预览和本机草稿能力，但完整的自定义流程执行尚不能作为本次已完成功能。历史文档中的旧后端或完整双层任务图设计，不自动等于当前版本已经运行。

## 7. 创新点

### 7.1 把陪伴接到具体行动上

Frost 不只回答问题，还能把明确请求交给地图、训练和饮食等入口。陪伴角色、动作入口与结果记录使用一套连续的交互逻辑，减少用户在不同页面重复解释自己的成本。

### 7.2 用城市探索承接日常习惯

地图是可以和伙伴一起活动的空间。种子、植物、角色动画和地点记忆把重复路线变成可回访的轻量游戏内容，让“出门走一走”获得更直接的视觉与情感反馈。

### 7.3 手机与小型硬件共享同一个角色

电子徽章不是另开一个聊天入口，而是把同一 Frost 会话延伸到实体按键、圆屏和声音。它探索了运动、散步等不方便持续触屏的场景，也保留了明确的开始、停止和权限边界。

### 7.4 将“模型建议”与“真实发生”分开

项目显式区分候选识别、用户确认、页面打开、任务执行和实际完成：餐食候选需要确认，地图就绪不等于 GPS 就绪，蓝牙 ACK 不等于真人听到声音。这种设计让 AI 陪伴能够保持亲切，同时对行动结果负责。

以上是本作品的设计组合与工程特点，不作“全球首创”或未经对比验证的性能领先声明。

## 8. 开发过程

本节按当前代码与现有开发记录梳理实现过程，不把整个项目描述为从比赛开始后才开发。

1. **建立城市探索基础。** 实现地图、角色配置与加载、同行动画、种子进度、种植和本机持久化，为中间 Earth 页面建立可交互的空间。
2. **形成统一伙伴入口。** 将文字对话、任务运行、Skill 注册、等待与取消、结果消息整合进 Frost；把页面和设备回执接入同一会话边界。
3. **连接运动健康场景。** 将 Photos 收敛到餐食记录，引入用户确认和份量修改；整合练了吗与 Her Motion，建立当天记录、长期目标和健康上下文之间的联系。
4. **扩展到手机与徽章。** 加入 Capacitor 原生桥接、实体按键音频链路、角色显示、语音反馈和真实定位语音交互；对断连、重复输入和取消作单独处理。
5. **收敛素材与发布流程。** 统一鸟类素材清单、保留已确认的画布样式和品牌图标，增加资源指纹、打包内容和源码一致性检查，避免新源码配旧资源。
6. **整理本次参赛交付。** 从当前工作区建立独立源码快照，撰写本文件，排除私人记录与凭据；测试和构建结果另记于本目录的验证记录，不沿用历史结果冒充本次验证。

## 11. 运行与复现

npm ci
npm --prefix lianlema-portable/app_project/app ci
npm --prefix vendor/her-motion ci

node deploy/pocketbuddy/build-coach-web.mjs
node node_modules/vite/bin/vite.js build --config vendor/her-motion/vite.config.ts
npm run build
